# Secrets reach the agent as a short-lived file path, never as a message, tool result or environment variable

An agent that needs a credential must be able to ask for one without the value entering conversation history. 0.11.2 offers two other channels and both fail: returning the value in an MCP tool result puts it in the transcript and in every later context window, and injecting it as an environment variable only happens in the `agent.session_open` hook, which runs at session start — forcing one mid-turn means daemon-client `refreshAgent`, which cancels the turn that is waiting for the answer. So a blocking request delivers a path to a `0600` handoff file instead: the agent reads the value with `$(cat <path>)`, the transcript carries only the path, and the file is deleted after 15 minutes, when the agent is archived, and when the plugin starts (a reload is a restart).

That file lives only in `/dev/shm`, verified with `fs.statfs` to be `TMPFS_MAGIC` before use, so a secret never reaches a persistent filesystem and there is nothing to scrub after a crash. There is deliberately no disk fallback: on a host with no usable `/dev/shm` — macOS, Windows, containers without one — `request_secret` fails with a clear error and no card is shown, because quietly writing a credential to disk to keep a feature working is the wrong trade. A third option, keeping the value in daemon memory and forcing every use through a plugin-run command, was rejected too: it breaks exports, `.env` writes and cross-turn use, and makes the plugin a command executor.
