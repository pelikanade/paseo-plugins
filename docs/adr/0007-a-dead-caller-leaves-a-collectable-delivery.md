# A delivery no live caller received stays collectable, and one pending request per agent

The tool blocks until the user answers, so the answer travels back on the call that is waiting. A provider-side MCP client can still give up first: it rejects the call with `-32001 Request timed out` and, in the SDK, first sends `notifications/cancelled` for that request id. The user goes on typing into a card whose caller is already gone, submits, and the value is written to a handoff file that no one reads — the timeline shows a tool error, the user believes the secret was handed over, and 15 minutes later the file is deleted with the value in it. Idempotency was keyed on the pending agent-and-label pair, so a retry under a reworded label stacked a second card instead of joining the first, and the plugin had no way to hand the value to a later call. This is recorded because it changes the meaning of "delivered" and of the retry contract the tool advertises.

Two decisions fix it. **Caller liveness is part of the request.** The gateway keeps the JSON-RPC id of each in-flight `tools/call` and aborts that call's controller when the client cancels it or when the response closes before the handler returns; a canceled waiter is dropped rather than counted, and a delivery counts as collected only when at least one live waiter received it. Delivery without a live waiter leaves the request _uncollected_. **An uncollected delivery stays collectable until its deadline.** A later call from the same agent under the same label returns the existing path instead of blocking again; a trailing qualifier such as `(retry)` is ignored when labels are compared, and a pending request is keyed per agent, so a retry before the user answers resumes the same card. The first caller that receives a path consumes it — after that the label starts a new request, so a rotated value is never silently replaced by the previous one.

Accepted consequences: the label is the recovery key, so a retry that rewords it beyond a trailing qualifier starts a new request and leaves the earlier value uncollected until its deadline; a client that abandons a call without a cancellation notification or a closed response still counts as live, which is the behaviour before this change; two connections of one agent that use the same JSON-RPC id concurrently can cancel each other's registration, whose failure mode is a delivery counted as uncollected, which the next same-label call then collects. Nothing about delivery itself changed: one `0600` file on tmpfs, deleted 15 minutes after delivery, when the agent is archived, and when the plugin starts.
